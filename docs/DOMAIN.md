## 2026-11-06 ~20:32 UTC — Step 4: grid layout, parameter ids, packing (real 12z files, eccodes keys)
- Fact: in both models the first grid point is latitude 90 and **longitude 180**, rows run south (`jScansPositively 0`), columns run east (`iScansNegatively 0`), last point lat -90, lon 179.75, increments 0.25, Ni 1440, Nj 721. So column 0 = 180 E (= -180) and column 720 = 0 E; it is NOT a 0..360 grid. Where learned: key dump of both files (`latitudeOfFirstGridPointInDegrees`, `longitudeOfFirstGridPointInDegrees`, ...). Checked: `pipeline.grid.latlon_to_index` gave the same flat index as `eccodes.codes_grib_find_nearest` for 12 points (incl. lon -182/360 wrap and both poles). The expected layout is in `config/pipeline.toml` [grid] and every message is checked against it.
- Fact: the unit difference of E006 is also a different parameter id: IFS `paramId 228` (tp, `m`), AIFS `paramId 228228` (tp, `kg m**-2`). eccodes gives both `shortName tp`. Where learned: `codes_get(h, "paramId")` on the first message of each file.
- Fact: both models pack `tp` with CCSDS at only 12 bits per value, and the packing step grows with the field's maximum (`binaryScaleFactor`). Examples (mm): IFS 0.061 at 6 h, 0.122 at 72 h, 0.244 at 120-240 h; AIFS 0.031 at 6 h, 0.125 at 72-240 h, 0.25 at 360 h. Each accumulated field is therefore rounded to that grid, so a de-accumulated 6 h value can be off by up to half the sum of two consecutive packing steps (IFS up to about 0.24 mm late in the run, AIFS about 0.125 mm up to 240 h). Where learned: `2**binaryScaleFactor` per message times the unit factor; the largest negative interval difference was exactly 0.50 of (this step + previous step) for both models, which fits rounding and nothing else.
- Fact: because of this rounding about 0.35 % of cell-intervals come out slightly negative after subtracting consecutive steps (most negative about -0.12 mm). They are set to 0 and counted. The mass this adds is 0.056 % (IFS) and 0.014 % (AIFS) of the total precipitation over the first 40 intervals (12z run). Consequence for D13: the 0.5 mm wet threshold is larger than the typical rounding error, but not by a big margin late in the IFS run.
- Fact: on the 12z and 00z runs of 2026-11-06 the area-weighted global mean over 0-240 h is 3.10 / 3.09 mm/day (IFS) and 3.16 / 3.15 mm/day (AIFS). AIFS has more light-rain cells: at >= 0.5 mm per 6 h 20 % (IFS) vs 27 % (AIFS) of cell-intervals are wet; at >= 0.1 mm 45 % vs 58 %.

## 2026-11-06 ~23:02 UTC — Front-end rendering facts (steps 6 and housekeeping)
- Fact: the 0.25 degree grid is regular in latitude and longitude, which is not linear in Web Mercator. An image drawn on a Mercator map must first be resampled so that each image row has the latitude a Mercator row would have; the spike does this by taking the nearest grid cell per row (`scripts/spike_frame.py`). Mercator ends at about 85.05 degrees north and south, so the polar caps are not drawn. Where learned: the spike frames and screenshots in `docs/evidence/`; the limit value is in `config/frontend.json`.
- Fact: MapLibre GL JS 6 needs WebGL2. Without it the console says "WebGL2 is required to display this map" and the page stays blank with no visible message (`docs/evidence/firefox-headless-maplibre-flat.png`, Firefox in a container without graphics support). Where learned: the Firefox attempt of 2026-11-06 (ENVIRONMENT.md).
- Fact: Natural Earth line data (world-atlas, 110m) contains segments that cross the 180 degree meridian. Drawn as they are, they appear as horizontal lines across the whole flat map; they must be split where neighbouring longitudes differ by more than 180 degrees (`frontend/src/geo.js`, tested). Where learned: the first MapLibre flat screenshot.
- Fact: a colour image of one 6 h interval (1440 x 1440 PNG, 8 steps of colour) is about 160 kB; the real size budget is measured in step 7. Where learned: `scripts/spike_frame.py` output.

## 2026-11-07 ~00:42 UTC — Step 8: how the plan reads the data (facts found by running things)
- **Blocks and local time:** a block's time is the END of a UTC-aligned 6 h interval. In India (+05:30) the blocks run 05:30-11:30, 11:30-17:30, 17:30-23:30 and 23:30-05:30. A block that crosses local midnight is given to the local day that holds its midpoint (rule D28). Checked in Node tests and on 8 real places against Python.
- **Stored values decide "wet" (D28):** values are stored in 0.1 mm steps, so "stored >= 0.5 mm" means raw >= 0.45 mm. On the real 12z run this moved the agreement shares to 17.6 % both wet, 64.6 % both dry, 17.8 % disagree (from 15.1 / 67 / 17-18). Source: `docker compose ... run --rm process` summary.
- **Forecast horizon from "now":** IFS has 40 blocks counted from the run time (10 days from the run), AIFS 60. A run is published about 7-8 h after its time, so from the moment a visitor looks, IFS covers fewer than 10 days; every 10-day total therefore ends with a stretch that only AIFS covers (the page shows it apart from the range).
- **Rounding:** Python's `round` sends halves to the even number, JavaScript's `Math.round` sends them up; for a latitude or longitude exactly between two grid cells they pick different cells. The browser code uses round-half-even; checked against 16 tricky places made by the Python code (`tests/frontend/fixtures/python_reference.json`).
- **Geocoder reply:** a name with no match returns an object WITHOUT a `results` key (not an empty list); `timezone` is an IANA name. Real request, 2026-11-07.
- **Zones on the check day (2026-11-07):** Chennai +05:30, London +00:00, Honolulu -10:00, Sydney +11:00, Quito -05:00, Anchorage -09:00, Auckland +13:00, Suva +12:00; written by the AI from tz rules, confirmed equal to what Node's ICU database returns (the check fails if they differ).
- **Browser behaviour:** headless Firefox leaves the geolocation permission prompt unanswered, and the page's own location timeout only starts after an answer, so the page keeps waiting; Chromium and WebKit refuse at once. A request made with `referrerPolicy: no-referrer` shows an EMPTY `referer` header in Playwright, meaning none was sent. All three engines decode the gzip tiles with `DecompressionStream`.

## 2026-11-07 ~10:45 UTC — MapLibre GL JS 6.16.0: globe to flat by a zoom expression (step 9.1, run in real browsers)
- The style `projection` can be an expression of the zoom, `['interpolate', ['linear'], ['zoom'], 2.5, 'vertical-perspective', 4.5, 'mercator']`; the map renders a globe when zoomed out and morphs to the flat map between zoom 2.5 and 4.5. Checked in Chromium 158 (software WebGL) and Microsoft Edge (real GPU). `map.flyTo({center, zoom, duration, essential: true})` ended exactly on the target in both ways tried (centre offset 0, zoom 4.500).
- The installed typings say the type `globe` "has internally switched to mercator" at high zoom and `vertical-perspective` "doesn't change to mercator"; so the morph uses `vertical-perspective` for the globe side.
- The 720 x 720 frames show 0.5 degree pixels: at zoom 4.5 each pixel is about 25 screen pixels wide at 1280 x 720 (blocky with `raster-resampling: nearest`).

## 2026-11-07 12:27 UTC — Picture quality facts (step 9.3b-1, measured)
- The forecast grid is 0.25 degree; a 720 px Web Mercator picture is 0.5 degree per pixel, so cells were lost or doubled; at the fly-in zoom 4.5 the map is about 11,585 screen pixels wide for the whole world, so a 1440 px picture is magnified about 8 times (each picture pixel about 8 screen pixels).
- Picture size is driven by the number of distinct colour contours, not only by pixel count: a smooth continuous gradient as 24-bit RGBA is 1.6 MB at 1440 px, the same picture as a 160-level palette PNG 0.7 MB, with 16 levels 0.39 MB (row filters chosen per row). Rain pictures of other blocks will differ (this was IFS +24 h of the 12z run), so the export prints the largest.
- MapLibre GL JS 6.16 raster layers support `raster-resampling` = `linear` or `nearest` and no colour ramp (`raster-color` is not in the installed typings), so the colours have to be in the picture.
- 50 m Natural Earth countries (world-atlas 2.0.2): 756 kB raw, 236 kB gzipped; 110 m: 108 kB raw, 39 kB gzipped.

## 2026-11-07 12:39 UTC — Real frame sizes and a sampling limit (step 9.3b-2, measured on the real export)
- Rain frame size varies with the weather: palette PNG at 1440 px with 16 gradient levels: median 292 kB, largest 495 kB over the 100 model frames of the 12z run; the agreement frames are about 90 kB. Size grows with the number of colour contours (rainier or more structured blocks), not with the pixel count (always 1440 x 1440).
- Bilinear up-sampling at exactly one picture pixel per grid cell puts the sample points half a cell away from the cell centres, so isolated single-cell peaks are shared by their neighbours (about 25 % of the value). A smooth field is reproduced exactly (a linear ramp is reproduced to 1e-4), values never leave the range of their neighbours, and the date-line seam is continuous (tests in `tests/backend/test_frames.py`).
- Palette PNGs (colour type 3 with a tRNS alpha table) are decoded by every browser tested (Chromium 158, Edge 157) and by MapLibre's image source; the rows use PNG filter types 1 and 2 chosen per row.

## 2026-11-07 13:29 UTC — Interpolating a rain field between grid cells (step 9.3c-3, seen in real pictures)
- Catmull-Rom (a common cubic) dips below zero next to a dry cell. Clamping that result to the range of the four neighbouring cells hides the negative values but cuts the curve flat along cell boundaries: dry areas then show straight, rectangular edges. A monotone cubic (PCHIP: the slope at a node is the harmonic mean of the neighbouring slopes, zero where they change sign) has no overshoot, is smooth across cell edges and passes through every cell value, so it needs no clamp.
- At zoom 7 one 0.25 degree cell is about 45 screen pixels wide, so any picture made once for the whole world is magnified about 40 times: sharpness has to come from drawing the view itself from the cell values.
- Drawing a 734 x 560 picture from about 12 x 10 cells with a separable PCHIP takes about 20-50 ms in a current browser (plain JavaScript, no GPU needed); the tiles for a view are a handful to a few dozen files of about 7 kB.

## 2026-11-07 14:02 UTC — The dark base-map style, measured (step 9.3d-2)
- The dark flavor of `@protomaps/basemaps` writes place names in `#7a7a7a` (cities), `#5c5c5c` (countries) and `#3d3d3d` (states) on land `#1f1f1f`: contrast ratios of about 4.2, 2.6 and 1.4 to 1 (WCAG formula), too dim to read on a dark map, as the user said. The flavor is a plain object of colours: our overrides are merged over it.
- A layer's `text-font` in this style is a conditional expression (`["case", ...]`) naming Noto Sans Regular, Medium or Italic: any check of "which fonts are used" must read the names inside the expression.
- Place names that have no English name are drawn in their own script (Arabic, Cyrillic and others), which needs glyph ranges beyond 0-1535 (range 65024-65279 was asked for in the Middle East); with `lang: en` that is the only reason for them.
- PMTiles over HTTP: the reader asks for parts of the file (range requests, answer 206); browsers cache such partial answers poorly, so a repeat visit still fetches most base-map tiles again (about 2.3 MB at zoom 7 in Edge).
