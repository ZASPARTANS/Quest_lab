## Context
- **What happened:** the push of 2026-11-08 11:35 UTC built twice and failed twice in the step that downloads the 190 MB map file from our own release (`ReadTimeout` talking to github.com, 60 s), during a GitHub incident ("Increase in timeouts for some unauthenticated users", from 10:36 UTC). - **User, 2026-11-08 ~11:55 UTC:** "y download something we dont need and already have ?" and, of my three options, chose **"1 and 2"**: (1) a cache between runs plus a retry, (2) fonts and sprites committed to our own repo.

The workflow has no cache. The map file is too big for git (100 MB per file limit).
- **Already in place and reused:** `fetch_release` (`pipeline/basemap.py:179`) returns at once when the file is already there and its size and sha256 match, so a restored cache needs no code change and is still verified (a poisoned cache cannot inject a wrong map). `fetch_assets` does the same per file against `config/basemap_assets.lock.json` (1029 sha256 entries, commit 028c18f713baecad…).
- **Order of work:** the already approved re-run of the failed build comes FIRST, when GitHub's incident is over (a monitor is polling GitHub's status page): it puts the design and the location fix on the live site for the user's phone test. This plan's changes come after, as further pushes.

## Security note (this plan)
It adds one GitHub-owned action (pinned) and removes one third-party download (fonts and sprites from the Protomaps repo at every build). Every stored file is still verified by sha256 before use (cache hit, release download and committed assets alike). The retry is bounded (3 tries, 30 s) and never retries an integrity failure. No secrets, no new permissions, no change to the public site's content. Pushes only to `ZASPARTANS/Quest_lab`; the one read of another repository's public page (the action's release) touches nothing there.
